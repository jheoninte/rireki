# 일본 이력서 템플릿과 작성 지원

## 1. 작성 가이드 데이터

`src/lib/resume-guides.js`는 UI와 분리된 언어별 필드 사전입니다.

```js
resumeGuides = {
  ja: {
    intro: {
      tip: 'STARで強みを裏付けます。…',
      example: '私の強みは課題を整理して改善を進める力です。…',
    },
  },
};
getResumeGuide('intro', locale);
```

예시는 가상의 작성 예시이며 실제 합격자 자료라는 주장은 하지 않습니다. 실제 사실에 맞춰 수정하도록 안내합니다. `HintButton`은 각 필드 아래에서 펼쳐지고 Escape로 닫히며, 기존 문구가 있으면 앱의 확인 모달에서 교체를 선택합니다. 반복 입력인 경력·학력·프로젝트는 클릭한 행만 수정합니다.

## 2. 컴포넌트와 데이터 구조

```text
Builder.jsx
├── TemplateSelector.jsx
├── AutoSaveIndicator.jsx ← useCloudResume.js
├── 필드와 반복 행 → HintButton.jsx ← resume-guides.js
├── TrustBadge.jsx
└── Resume.jsx
    ├── ModernResume (기존)
    ├── resumes/RirekishoResume.jsx
    └── resumes/WorkHistoryResume.jsx
```

기존 저장 문서와 DB 검증을 유지하기 위해 내부 ID는 `rirekisho`(履歴書), `work-history`(職務経歴書)를 사용합니다. 일본어에서는 일반·전직용, 신졸·인턴용, 아르바이트·파트용, 재취업용과 직무경력서의 5가지 용도별 서식을 선택합니다. 기본값은 첨부 양식의 일반·전직용 履歴書입니다. 기존 모던 서식을 가리키는 URL이나 저장 설정은 일본 기본 서식으로 정규화하며 입력 데이터는 유지합니다. 다른 국가용 기존 렌더러는 코드에 남겨 두되 일본 페이지에 노출하지 않습니다. 서식을 전환해도 `data`를 초기화하지 않습니다. `resume-data.js`의 정규화로 기존 초안에도 새 필드의 기본값을 제공합니다.

`resume-markets.js`에서 언어별 기본 서식·허용 서식·첫 화면을 관리합니다. `Landing.jsx`는 시장별 페이지 등록부를 통해 일본 전용 `JapaneseLanding`을 선택합니다. 한국어·영어 설정은 분리된 초안이며 아직 공개하지 않습니다. 일본어 서비스명은 履歴書作成ツール이며, 첫 화면은 블루 버튼과 문서 중심 미리보기, 용도별 카드 목록으로 구성합니다. 스마트폰 모형과 원형 장점 구성은 제거했습니다. 용도 필터는 네이티브 라디오와 CSS로 동작하므로 JavaScript가 제거된 정적 랜딩에서도 사용할 수 있습니다.

`PhotoUploader.jsx`는 JPG·PNG 5MB 이하의 증명사진을 받습니다. 미리보기에서 확대와 좌우·상하 위치를 조절하고, 적용할 때 브라우저 Canvas로 450×600 JPEG를 생성합니다. 적용 전 취소하면 기존 사진을 보존하며 사진 교체·삭제도 가능합니다. 같은 3:4 사진이 브라우저 미리보기, PDF, Word에 사용됩니다. Word 사진 크기는 108×144px(약 28.6×38.1mm)입니다. 사진과 성별은 진행률의 필수 항목에 포함하지 않습니다.

프로젝트는 `projects: [{ projectName, projectPeriod, projectRole, projectStack, projectResult }]` 형태입니다. 직무경력서의 미리보기와 Word 모두 프로젝트 및 기술 스택 표를 출력합니다. 새 UI 문구는 `src/i18n/builder-features-ja.js`에서 관리합니다. 현재 프로젝트가 등록한 언어는 일본어이며 새 언어는 i18n 카탈로그와 가이드 사전을 함께 추가하면 됩니다.

## 첨부 양식 기준

참조 파일: `【標準的な履歴書】厚生労働省の履歴書テンプレート.docx`.

- A4 2쪽, 연도·월이 분리된 학력·경력 15행 + 연속 7행, 면허·자격 6행입니다.
- 성별은 선택 기재이며 만 나이, 현주소와 별도 연락처의 후리가나·전화·E-mail을 구분합니다.
- 지원동기·특기·자기PR는 원본의 하나의 칸에 합쳐 출력합니다. 본인 희망란은 분리합니다.
- 통근시간·부양가족·배우자 항목은 원본에 없어 추가하지 않았습니다. JIS_Rirekisho는 기능 식별을 위한 이름이며 별도 인증을 의미하지 않습니다.
- Word는 `public/templates/mhlw-rirekisho.docx`에 보존한 원본의 표·셀·쪽 설정·사진 도형에 플레이스홀더를 채웁니다. `rirekisho-word.js`가 이 경로를 담당합니다.
- PDF는 명시적인 2개 A4 페이지를 각각 렌더링합니다. 일반 템플릿의 임의 높이 자르기를 사용하지 않습니다. 행 수·문자 수 초과와 PDF 페이지 넘침은 출력 전에 차단하며 데이터를 잘라 버리지 않습니다.
- 각 학력·경력 행은 하나의 연월·사건으로 작성합니다. 기존 기간 문자열은 유실 방지를 위해 나머지 문구를 내용 칸에 유지합니다.

원본의 OOXML 항목과 표 구조를 확인했고 브라우저의 두 페이지 배치를 시각 확인했습니다. 프로덕션 미리보기에서 합성 테스트 증명사진을 업로드해 PDF·Word를 실제 다운로드했습니다. PDF의 두 A4 페이지를 이미지로 렌더링해 사진과 배치를 확인했으며, Word의 5개 표·사진 관계·플레이스홀더 치환을 검증했습니다. Word 렌더러는 번들 LibreOffice가 없어 실행하지 못했으므로 Word의 픽셀 단위 일치 검증은 완료되지 않았습니다.

## 3. 자동 저장과 신뢰 표시

`Builder`가 기존 Supabase 훅과 상태 표시를 통합합니다. `VITE_CLOUD_ENABLED=true` 및 인증·DB 설정이 필요합니다. 최초 저장 또는 불러오기 선택으로 클라우드 동기화가 활성화됩니다. 기존 클라우드 문서가 있으면 로컬 문서를 자동으로 덮어쓰지 않습니다.

입력이 멈춘 뒤 2,000ms가 지나면 저장합니다. 대기·저장 중·저장 완료·오류·충돌을 구분하며 성공 응답 이후에만 저장 완료를 표시합니다. 완료 시각을 상대 시간으로 갱신합니다. 저장 중 새로 입력한 내용은 다음 요청으로 보내며 서버의 revision 검사를 사용합니다. 충돌·오류 후에는 자동 업로드를 중단하고 재확인할 수 있습니다. 게스트 또는 클라우드 비활성 환경에는 클라우드 저장 완료를 표시하지 않습니다.

배지는 현재 구현에서 확인 가능한 계정별 접근 제어와 기업으로의 자동 전송 방지, 브라우저 저장 범위를 설명합니다. 브라우저 localStorage는 평문이고 종단간 암호화가 구현되지 않았으므로 ‘모든 정보 암호화·본인만 열람’이라는 단정적 문구는 사용하지 않습니다. Supabase 서비스 운영자 접근까지 불가능하다는 보장도 하지 않습니다.

검증은 전체 Vitest 테스트와 프로덕션 빌드로 수행합니다. Supabase 네트워크 동작은 훅 테스트에서 모의 응답으로 검증하며 실제 운영 계정에 저장하지 않습니다.


## 지원 상황별 서식

`src/lib/japanese-templates.js`가 ID·용도·추가 입력 필드·출력 제목을 함께 정의합니다.

| ID | 용도 | 입력·출력에 반영하는 내용 |
| --- | --- | --- |
| `rirekisho` | 일반·전직 | 첨부된 후생노동성 표준 항목 |
| `rirekisho-graduate` | 신졸·인턴 | 학업·세미나·연구, 학생 시절 집중한 경험 |
| `rirekisho-part-time` | 아르바이트·파트 | 근무 가능 요일·시간대·시작일 |
| `rirekisho-return` | 재취업 | 재취업 준비 활동과 희망 근무 조건 |
| `work-history` | 직무경력서 | 담당 업무·실적·프로젝트·기술 |

일반 서식의 항목은 유지합니다. 나머지 이력서는 원본의 페이지·이력 표·사진란을 공통으로 쓰고, 자기PR와 본인 희망란의 제목 및 본문을 용도에 맞게 조정합니다. 모든 파생 서식이 후생노동성 원본과 동일하다는 주장은 하지 않습니다. 대학·지원처 지정 양식이 있으면 이를 우선하도록 안내합니다. 재취업 시 개인적인 공백 사유나 병력·가족 사정을 요구하지 않습니다.

신규 필드는 `resume-data.js`의 정규화를 거치며 템플릿을 바꿔도 보관합니다. 출력에는 현재 서식에 해당하는 필드만 포함합니다. PDF와 Word는 동일한 `rirekishoPR`/`rirekishoPreferences` 조합을 사용합니다. 합계 360자/180자 제한은 용도별 추가 문구도 포함하여 검사합니다.

새 ID의 클라우드 저장에는 `supabase/migrations/202611200003_applicant_templates.sql`을 적용해야 합니다. 기존 인증·행 접근 제어·revision 충돌 검사는 유지하며, 실제 PostgreSQL 테스트로 신규 ID 저장 및 오래된 revision 거부를 확인했습니다. 이 작업에서 원격 DB에는 마이그레이션을 실행하지 않았습니다.

현지 서비스의 용도 분류는 [ヤギッシュ 템플릿 목록](https://rirekisho.yagish.jp/static/rirekisholist/)을 참고했습니다. 외부 사이트의 화면·이미지·로고·문구는 복제하지 않았습니다.
